# Flow 設計メモ

2026-09-13 時点の方向性。実装前の合意事項をまとめたもので、コードが追いついたら本文を更新する。

## 目指すもの

企画から校正までの執筆工程を、コーディングエージェントが「書く → 検証で落ちる → 直す」を繰り返すのと同じ形で回すライティングエージェント。参照体験は NotebookLM のレポート機能(ソースに根拠を置いた多段生成)。

## 中心の設計判断: 判定器を先に作る

コーディングエージェントが自走できる理由は、ビルドとテストという機械的な判定器があるから。文章にはこれが素で存在しないため、判定器なしにループさせると、LLM が自分の出力を自己評価して収束したふりをする失敗が起きる。

Flow は判定器を3層で持つ。

| 層 | 判定内容 | コーディングでの対応物 |
|---|---|---|
| ソース照合 | 本文の主張がソースに根拠を持つか。ソースに無いことを書いたら落ちる | 型チェック |
| 機械チェック | 単語親密度による硬い語の検出、二重否定・「の」の連鎖などの構文ルール。決定的に判定できる | lint |
| 受け入れ基準 | 企画で固定した「読者は誰か」「読後に何ができるようになるか」「書かない範囲」に照らす | 受け入れテスト |

機械チェックの元ネタは、既存のスキル `ja-wording-lint` と `meiseki` の判定ルール。

## 人間が関わる場所

人間が介入するのは企画工程だけ。企画は人間とエージェントが一緒に詰める。人間が丸ごと書くと重くて始まらず、エージェント任せだと受け入れ基準が空洞になるため、その中間を取る。以降の工程(構成、初稿、推敲、校正)は判定器に対して自動で回す。

コーディングエージェントのプランモード(人間と合意)と実装(自走)の分け方に対応する。

## 企画工程の出力はファイル

企画の合意は会話ログではなく、判定器が読めるファイルとして残す。含める項目:

- 読者
- 読後にできるようになること
- 扱うソース
- 書かない範囲

後続の全工程がこのファイルを参照し、校正工程はこのファイルに対して合否を出す。ファイルにしないと、ループの途中でエージェントが企画を都合よく解釈し直すのを止められない。仕様と受け入れテストを一つのファイルに同居させる形。

## フェーズ

| Phase | 内容 | 終了条件 |
|---|---|---|
| 1a Tooling ([#1](https://github.com/sumx21t-3310/Flow/issues/1)) | `Flow.CLI` 一本で、エージェントがツールを呼べる配管を通す | CLI 引数、File IO、ネット検索がツールとして呼べる |
| 1b Loop ([#2](https://github.com/sumx21t-3310/Flow/issues/2)) | 工程1つ × 判定器1層で最小ループを回す | 「書く → 落ちる → 直す → 通る」が1回まわる。ソースと企画ファイルは不要 |
| 2 Core 分離 + Pipeline | `Flow.Core.*` を別 csproj へ移し、工程を連結する設計を決める | CLI が Core を参照するだけになり、企画 → 校正まで工程の出力が次工程へ渡る |
| 3 Desktop | Avalonia で2つ目のフロントエンドを作る | 未定。「CLI ではできない何を、誰が、いつ」が一文で言えたら要件にする |

POC は 1a と 1b の2段。1a は Agent Framework が担う部分なのでリスクは低い。設計が成立するかを決めるのは 1b で、ここが POC の本当の終了条件。

用語の使い分け:

- **Tooling**: エージェントがツールを呼べること(1a)
- **Loop**: 1工程の中で判定器に対して書き直しを繰り返すこと(1b)
- **Pipeline**: 工程を縦に連結し、出力を次工程へ渡すこと(Phase 2)

Phase 1 の間、csproj は増やさず名前空間だけ `Flow.Core.*`(判定器、工程、企画ファイル)と `Flow.CLI.*`(引数処理、表示)で分けて書く。POC 中に境界を守っておけば、Phase 2 の分離はファイル移動と参照追加で済む。

## 未決定

- 各工程の粒度と、工程間でやり取りする成果物の形
- ソース照合の実装方法(引用の単位、根拠なしと判定する閾値)
- 1b で使う工程と判定器の組。候補は校正 × 機械チェック(手順が既に言語化されているため)
